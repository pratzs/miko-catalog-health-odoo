# Miko Catalog Health for Odoo

**LIVE on the Odoo Apps Store since 2026-08-03.** Our first product on a marketplace
other than Shopify.

Validates every barcode in an Odoo product catalog against the GS1 check-digit
standard, reports the digit each broken one should have ended with, and flags the
fields that are simply not filled in.

## Why it exists

Odoo enforces that a barcode is *unique*. It never checks that the number is
*valid*. A barcode with a wrong check digit saves without complaint, looks normal
in a list view, and fails at the scanner.

Verifiable, and it is the listing's lead: **the demo data that ships inside Odoo
contains two ITF-14 barcodes with an incorrect check digit.**

- `Office Lamp` `40164785534112` should end in **7**
- `Flipover` `40164785512001` should end in **9**

Install on a fresh database with demo data and it finds both.

```
miko-catalog-health-odoo/
  miko_catalog_health/     <- THE SOURCE OF TRUTH. Written against Odoo 19.
  build/14.0 ... 19.0/     <- GENERATED by _dev/build_versions.py. Never edit.
  publish-repo/            <- git clone pushed to GitHub, one branch per series.
  dist/                    <- zips, reference only. Odoo does NOT use them.
  _dev/                    <- Docker harness, render scripts, test logs. Not shipped.
```

Editing anything under `build/` or `publish-repo/miko_catalog_health/` loses the
change on the next build. Only `miko_catalog_health/` is real.

## The release cycle

Everything runs locally in Docker against a throwaway Postgres. Nothing touches a
client system.

```bash
cd _dev && docker compose up -d db
python3 build_versions.py          # regenerate all six series from source
```

Test one series:

```bash
docker run --rm --network dev_default \
  -v "$PWD/../build/19.0":/mnt/extra-addons:ro odoo:19 \
  odoo --addons-path=/usr/lib/python3/dist-packages/odoo/addons,/mnt/extra-addons \
  --db_host=dev-db-1 --db_user=odoo --db_password=odoo \
  -d test19 -i miko_catalog_health --without-demo=False \
  --test-enable --test-tags /miko_catalog_health --stop-after-init
```

Odoo 14 and 15 have no arm64 image; on Apple Silicon add `--platform=linux/amd64`.

**Certify all six before any release.** Write to log files rather than capturing in
`$(...)`: command substitution silently drops the summary line for the emulated
amd64 runs, which once made two passing series look like failures. Logs land in
`_dev/testlogs/`.

Browse it at http://localhost:8069 (`admin`/`admin`) after `docker compose up -d odoo`.

### Publishing an update

1. Edit `miko_catalog_health/` only.
2. `cd _dev && python3 build_versions.py`
3. Certify all six series.
4. Copy each `build/<series>/miko_catalog_health` into `publish-repo`, commit on the
   matching branch, push.
5. **Press Scan on every row** at https://apps.odoo.com/apps/dashboard/repos.
   Odoo does not poll. Nothing happens until you scan.

Full runbook and traps: `PUBLISHING.md`.

## What differs between series, and how one source covers them all

| Difference | Affects | Handling |
|---|---|---|
| `<list>` element | 18+ only | build rewrites to `<tree>` for 14 to 17 |
| `column_invisible` | 17+ only | rewritten to `invisible` for 14 to 16 |
| `expand`/`string` on search `<group>` | removed in 19 | bare `<group>`, valid everywhere |
| `flush_model()` | 16+ | runtime `hasattr` fallback to `flush()` |
| `flush_recordset()` | 16+ | runtime `hasattr` fallback to `flush()` |
| `env.invalidate_all()` | 15+ | test helper falls back to `env.cache.invalidate()` |
| Barcode uniqueness | SQL constraint on 14/15, Python constraint on 16+ | test detects which and adapts |

Version-shaped differences are handled at **build time**; API differences at
**runtime** with `hasattr`. That keeps one readable source.

## Correctness, and why we can claim it

Two failure modes would destroy trust faster than any missing feature: flagging a
correct barcode, or suggesting a fix that is still wrong. Both are tested, and the
tests ship so a merchant can run them.

- **Real barcodes.** Published GS1 codes in circulation across all four
  symbologies. None is flagged.
- **A second implementation.** The standard is implemented twice, independently and
  in opposite directions: the shipped one walks the body right to left, the
  reference walks it left to right deriving weights from length. **400,000
  generated barcodes, zero disagreements.**
- **Round trip.** For every body, the digit we suggest produces a valid barcode and
  all nine others are correctly rejected.

### Deliberate non-flags

Reporting a merchant's own convention as breakage is the false positive most likely
to get the module uninstalled. These are reported but never counted:

- **Internal codes** such as `CUP-FILT-100`, and any non-GTIN length.
- **Services**, which have nothing to scan, shown as *Not applicable*.
- **Zero cost price**, legitimate in plenty of businesses.

## Things that cost real time, so they are written down

**Only a live install found these.** Not one was visible by reading the code.

- **The manifest version is pinned to the series.** `Invalid version '19.0.1.0.0'.
  Modules should have a version in format ... 18.0.x.y.z`. One directory cannot
  serve six versions, which is why `build_versions.py` exists.
- **Odoo 19 dropped `expand` and `string` from search `<group>`.** The old spelling
  fails RelaxNG and takes the whole module down at install.
- **`image_1920` is not a column.** It is a `fields.Image` stored in
  `ir_attachment`. Reading it per record in a compute pulls every binary out of the
  filestore. The compute resolves image presence with one id-only query instead.
- **`barcode` lives on `product.product`,** not the template. It is a related field.
  Raw SQL fixtures must invalidate the whole environment, not just the template
  recordset, or the compute reads a stale cached value.
- **Stored computes do not backfill.** A catalog imported before install stays
  unchecked until `Rescan Catalog` runs once. That is why the menu exists.

## Hosting support

| Platform | Supported | Why |
|---|---|---|
| On premise | Yes | Certified on 14 to 19 |
| Odoo.sh | Yes | Same runtime, no filesystem writes, no external calls |
| Odoo Online (SaaS) | **No** | Odoo Apps FAQ: third-party apps "cannot be used on Odoo Online, unless they are data-modules (that do not include any python files)" |

The data-module exception is the only door and it is shut to us: check-digit
arithmetic cannot be expressed as views and data. No restructuring gets this onto
Odoo Online. **Stated on the listing** so nobody installs, fails, and leaves a
one-star review.

**If someone says they are on Odoo Online, probe before believing it.** People
routinely call a managed Odoo "Odoo Online" when it is actually self-hosted, which
is why App Store modules install for them. `/web/database/manager` returning 200
proves self-hosting; neither Odoo Online nor Odoo.sh ever exposes it.

## Branding

A Miko app. Two rules so the family scales past this first one:

1. **Colour identifies the app, never the platform.** Plum belongs to Catalog
   Health, not to "Odoo". No colour is ever reused.
2. **The platform lives in the name**, `Miko <Thing> for Odoo`. The mark itself is
   never modified.

Odoo apps draw their unique colour from a reserved berry band anchored on Odoo's
own `#714B67`. Full band and what is taken: memory
`reference-miko-odoo-app-family-colours`.

The banner's brand accent is **this app's colour**, like every Shopify app banner.
Tripster red appears only in the lockup's "by Tripster Developers" line. Semantic
colours never swap: error red stays red.

Assets live in the canonical places, not in this repo:

- `Apps/Miko App Icons/Miko Mark/icon-catalog-health-plum.png` (and `-web`)
- `Apps/Miko App Icons/Miko Catalog Health Banners/`

Generated with the established script, never freehand:

```bash
NODE_PATH=<repo>/Apps/miko-image-resizer/node_modules \
  node make-icon.cjs catalog-health-plum '#9A6C8D' '#714B67'
```

Banner and screenshots are built in HTML/CSS then captured with headless Chrome per
the standing image pipeline, never PIL primitives. Sources in `_dev/render/`.
