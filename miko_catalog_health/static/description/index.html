Odoo checks that a barcode is unique. It never checks that it is valid.

Every retail barcode ends in a check digit, calculated from the digits before it. Get that one digit wrong and the number still looks perfectly normal in a list view, still saves without complaint, and still fails at the scanner. Nobody finds out until someone is standing at a till or a receiving bay with a product that will not go through.

Odoo enforces uniqueness on barcodes, so it will stop you entering the same one twice. It does no arithmetic on them at all. A transposed pair of digits during a supplier import, a hand-typed number, a spreadsheet that dropped a leading zero: all of it saves cleanly and sits in your catalog until it costs you time at the counter.

This is not hypothetical. The demo catalog that ships inside Odoo 19 itself contains two ITF-14 barcodes with an incorrect check digit. Install this module on a fresh Odoo database with demo data and it finds both of them in the first scan.

Find every broken barcode, and the digit that fixes it

Catalog Health validates every barcode in your catalog against the GS1 modulo-10 standard and tells you, for each broken one, exactly which digit it should have ended with. You are not left to work it out yourself.

Filtered to barcodes that will not scan. Flipover and Office Lamp are Odoo's own demo products.

And the gaps that quietly break everything else

While it is reading the catalog it also reports what is simply not filled in. Each product gets an issue count, and the list opens with the worst offenders first so there is an obvious place to start.

It does not cry wolf, and we can show our working

A tool that flags correct data, or hands back a fix that is still wrong, is worse than no tool. Both failure modes are tested rather than asserted, and the tests ship inside the module so you can run them yourself.

Checked against real barcodes

Products in circulation with known good check digits, across all four symbologies. None of them is flagged.

Checked against a second implementation

The standard is implemented twice, independently and in opposite directions. Across 400,000 generated barcodes the two never disagreed once.

Every suggested fix round trips

For each broken barcode, applying the digit we suggest produces a valid barcode, and all nine other digits are correctly rejected.

Your conventions are respected

Internal codes and service products are reported for visibility and never counted as defects.

Run the suite yourself with --test-enable --test-tags /miko_catalog_health. It covers 20 cases and is run against Odoo 14 through 19 before every release.

Fix them where you found them

The audit list is editable. Correct a barcode, add the missing reference, set the price, and the status recalculates immediately. There is no separate wizard to learn and no export and reimport cycle.

  • Filter to one kind of problem at a time, so a session has a clear end point.
  • Group by barcode check or by product category to see where the rot is concentrated.
  • Run Rescan Catalog once after installing, so products that were imported before the module existed get checked.

What it deliberately does not do

Being clear about this is more useful to you than a longer feature list.

  • It does not generate barcodes or buy GS1 prefixes for you. It validates what you already have.
  • It does not send your catalog anywhere. There is no external service, no API key and no account. Everything runs inside your own database.
  • It does not write to your products on its own. It reads, it reports, and you decide what to change.
  • It adds no new models and no new access rules, so it changes nothing about who can see what.

Each series is a separate build, installed into a clean database of that exact version and run through the full test suite before release. None of these numbers is an assumption carried over from another version.

Two behaviours genuinely differ across that range, and the module adapts rather than pretending they do not:

  • Duplicate barcodes. On 14 and 15, Postgres refuses a duplicate outright, so one cannot exist. From 16 the check moved into Python, which a bulk import can bypass. The duplicate report therefore matters on 16 and later, and is simply never triggered on 14 and 15.
  • Product types. What counts as a service, and therefore has no barcode to check, is read from your Odoo rather than hard coded, so the exclusion stays correct as the field changes shape between versions.
